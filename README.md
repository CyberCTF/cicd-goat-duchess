# Duchess: a leaked PyPI token (CyberCTF lab)

A bespoke, self-contained reproduction of the **Duchess** challenge from
[CI/CD Goat](https://github.com/cider-security-research/cicd-goat) — OWASP **CICD-SEC-6,
Insufficient Credential Hygiene**. Wonderland's `duchess` repository is a small Python package.
A PyPI upload token was once committed to it by accident and later removed, but the removal only
touched the current branch: the token still sits in a past commit, where anyone with read access
can recover it.

**Private lab content — do not copy into any public repository.**

## Infrastructure

One machine, a lightweight git server:

| Machine | What |
|---|---|
| `git` | nginx serving the bare `duchess.git` repository over HTTP (the git "dumb" protocol — enough to `git clone` and browse history). `git` + `curl` are present for the in-machine solver check. |

No Gitea, Jenkins or GitLab — only what the vulnerability needs. The git service listens on
container port 3000; the host port is assigned dynamically by the runner (see below).

## Objective

One per-player objective (`.ctf/objectives.json`), graded by CyberBackend:

| Key | Evidence | What the player recovers |
|---|---|---|
| `duchess` | `SECRET` (`%s`) | the leaked PyPI upload token, recovered from the repository's git history |

Intended path: clone the repo → notice `.pypirc` is gone from the tip but was committed earlier →
read the token from that historical commit (`git log -p`, `git show <commit>:.pypirc`, or a secret
scanner such as `gitleaks`). The token is the flag.

## Per-player flag

The token is issued per player by CyberCTF and handed to the lab by the launcher as a **file**
(`isoloom.yml` `inputs: [CTF_FLAG_DUCHESS]`, delivered via `files: [{ input: CTF_FLAG_DUCHESS }]`),
never an environment variable, so it never appears in `docker inspect`, an image layer or a
generated file. The git machine's `setup` step (`build/git/seed-history.sh`) reads the file once
and builds the repository's history with the token leaked in a past commit and removed at the tip.

An **offline start** (local, CI) leaves the input empty, and the lab seeds its development
placeholder (`.ctf/objectives.json` `dev`) instead, so it still comes up and is solvable without a
launcher.

## Dynamic port

The git service declares `ports: { http: { port: 3000, protocol: http, publish: true } }`.
`publish: true` asks the runner for a **free host port it picks at `up` time** — there is no fixed
host port anywhere in the spec, message, configs or checks. The `message` reads the real URL back
through `{{ machines.git.ports.http.url }}`.

## Run it

Described once in [`isoloom.yml`](isoloom.yml) ([Isoloom](https://www.isoloom.com)); run on Docker
through the [Isothrum](https://www.isothrum.com) runner:

```bash
isoloom validate .
isoloom generate . --target docker
isothrum up . --target docker          # add --secret-from-env CTF_FLAG_DUCHESS for a real value
isothrum check . --target docker
isothrum down . --target docker
```

Solve it the way the check does (clone and scan history):

```bash
git clone <the URL the message prints>duchess.git
cd duchess && git log -p -- .pypirc    # the token is the password in the historical .pypirc
```

## Layout

- `build/git/Dockerfile` — alpine + nginx + git + curl
- `build/git/nginx.conf` — serves the bare repo over HTTP (dumb protocol)
- `build/git/seed-history.sh` — the `setup` step: builds the repo history, leaking the per-player token into a past commit
- `build/git/solve.sh` — the solver / self-check (`/usr/local/bin/duchess-solve`): clones over HTTP, proves the token is recoverable from history and gone from the tip, never prints it
- `build/git/repo-src/` — the original `duchess` Python package committed across the history
- `.ctf/` — `metadata.json` and `objectives.json` (the catalogue registration)
- `UPSTREAM.md` — attribution for the reproduced challenge
- `.isoloom/` — generated by `isoloom generate` (git-ignored; don't edit)
